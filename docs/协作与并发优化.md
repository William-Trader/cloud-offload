# 协作与并发优化研究（Cloud Offload）

目标：让「本地 agent ↔ 云端算力」这条链路**真正省 token**，而不是把预算耗在双方的往返沟通上。

## 1 先度量：一次调用的开销分解

以一次标准调用为例（实测，账本 v3 口径）：

| 组成 | token | 是否本地负担 |
|---|---|---|
| 指令（本地打字） | 14 | 是（不可省） |
| 云端产出 | 26 | 否（本来要本地写） |
| 系统提示（网关加，发往云端） | ~60 | 否（云端侧，免费） |
| 回执（回到本地上下文） | 4 | 是（协议开销） |

结论：本地真实负担 ≈ 指令 14 + 回执 4 = **18**；若本地自做 ≈ 14+26 = **40**。协议开销占比 **9%**，已是可接受区间；优化前回执约 25 token，占比 38%。

## 2 优化清单（按 ROI 排序）

### O1 结果缓存（已实现，ROI 最高）
相同 task+material+model 命中缓存 → **0 次云端调用、0 等待**。
实测：第二次同题 `cached=true, ms=0`，省 40 token、省 5.2s。
接口：GET /api/cache（规模）、DELETE /api/cache（清空）。

### O2 会话卫生 / 自动重置（已实现，ROI 极高）
网页会话历史会累积并被每轮拖动。实测同一 4 字任务：**7s → 223s**。
修复：回答块 > 36 自动导航到新会话；并暴露 POST /api/reset。
收益：单次耗时回落 **2.7s**，且避免把历史 token 白白送进云端。

### O3 协议瘦身（已实现）
回执从"回执：已写入文件（NNN 字符, M ms）"压到"OK NNN字/Ms"：**~25 → ~4 token**。

### O4 输入+输出全纳入统计（已实现）
节约 = est(指令) + est(材料) + est(产出)。材料越长，节约越大 —— 因为本地根本不用读它。

### O5 分段并行（已实现于长文流水线）
长文（如插画/报告）拆成互相独立的子任务，逐段生成再本地拼装。
实测：一段 3.8k 字符的插画分组，每段 42–60s 独立完成，显著优于一次长生成（后者会被长思考截断）。

### O6 页池并发（设计 + 权衡，默认关闭）
现状：单浏览器页 + 全局锁（withLock），**串行**，吞吐约 2–4 请求/分钟。
可做：维护 N 个 chatglm 标签页 + 按页加锁，把吞吐提到约 N 倍。
**代价**：与防封号策略冲突（最小间隔 15s、每日上限），并发会显著提高风控概率。
建议：仅在**批量离线任务**场景开启（如夜间批量翻译），日常保持串行 + 缓存优先。

### O7 路由前置（已实现）
小任务/敏感内容在**本地**就判掉，根本不发云端：阈值 + 类型白名单 + 保护规则。

## 3 收益汇总（实测）

| 优化 | 指标 | 改善 |
|---|---|---|
| O1 缓存 | 重复任务 | 调用 1 → 0，耗时 5.2s → 0ms |
| O2 会话重置 | 单次耗时 | 223s → 2.7s |
| O3 协议瘦身 | 回执 token | ~25 → ~4 |
| O4 全量口径 | 节约统计 | 只看产出 → 输入+输出 |
| O6 页池（理论） | 吞吐 | ×N（受风控约束） |

## 4 并发视角：为什么现在串行是对的
1. 同一账号的并发请求会相互打断（同一页面 DOM 只能承载一个流），必须先做页隔离。
2. 页隔离后，风控角度看是"多标签同时提问"，比串行更显眼。
3. 因此**并发不是免费的**：它用封号风险换吞吐。
4. 正确顺序是：缓存 → 会话卫生 → 协议瘦身 → 分段独立化 → 最后才考虑页池。

## 5 结论
链路开销已从 38% 压到 9%；重复任务零成本；长任务不再被历史拖慢。
下一步若要做高吞吐，建议先落地"离线批量 + 页池 + 更保守的节奏"，而不是直接提高日常并发。
