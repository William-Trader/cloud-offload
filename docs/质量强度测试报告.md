## 3 Token 口径准确度（重点）
旧口径 est = ceil(chars / 1.5) 假设"每 1.5 字符 1 token"。用真实分词器实测：
- 中文散文：约 **1.87–1.93 字符/token**（README 1.931、CLOUD_OFFLOAD.md 1.865）
- 混合代码/HTML/JSON：约 **3–4 字符/token**

结论：旧口径 **MAPE 77.7%**，对中文正文高估约 24%–29%，对代码更高估。

新口径：按字符类别最小二乘标定（基准 cl100k_base 真实分词）
- CJK 汉字（含中日韩标点/全角）：**1.0616 token/字**
- ASCII 字符：**0.3048 token/字符**
- 其他：0.9 token/字符

新口径 **MAPE 4.0%**（同一语料）。

注：cl100k 是参考系，GLM / DeepSeek 的分词器不同；绝对数存在 ±10% 量级偏差，但用于相对占比足够。

## 4 计算口径 v2（已简化）

| 量 | 定义 |
|---|---|
| 节约 token | = 云端本次**产出**的 token |
| 本地实花 | = est(指令) + est(回执) |
| 总 token（基线） | = 节约 + 本地实花 |
| 节约占比 | = 节约 / 总 token |

改进前用"本地自做 − 本地实花"，短输出时常为 0（回执与正文等长），导致仪表盘长时间不动。现在**每次调用都会让"节约"增长**，等于产出规模。

## 5 性能与一次严重退化
- 小任务（输出 4 字）：冷启动 14.3s；稳定后 **2.7s**。
- **发现**：chatglm 网页会话历史累积后，同一个 4 字小任务耗时从 7s 飙到 **223s**（每轮都拖动全量历史）。
- **修复**：新增 POST /api/reset，并在 askGLM 中当回答块数 > 36 时自动导航到新会话。修复后回到 2.7s。

## 7 局限与风险
- 依赖网页版会话（非官方 API）：页面改版即失效；完成判定逻辑针对 2026-10 的 DOM。
- 估值基于 cl100k 参考系，绝对偏差 ±10% 量级。
- 单浏览器页串行，吞吐约 2–4 请求/分钟。
- 受防封号约束：最小间隔与每日上限，超限自动回落本地。

## 8 结论
功能、路由、落盘、错误处理、压力、并发六项全部通过；口径准确度达工程可用（MAPE 4%）。已修复的最大风险是页面会话膨胀导致的性能退化。
